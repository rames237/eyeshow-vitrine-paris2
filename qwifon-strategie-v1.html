Qwifon · Strategic Build Brief

Machine de distribution digitale — Cameroun

Synthèse opérationnelle des recherches croisées : architecture V0/V1, points de consensus, divergences à tester et structure de Build/Test pour l’agent d’exécution.

Document public statique : aucun cookie, aucun tracker, aucune authentification. Les marges, SLA, minimum deposits et droits de sous-distribution restent des hypothèses tant qu’ils ne sont pas confirmés contractuellement.

1. Décision stratégique actuelle

Le projet n’est pas « une app de recharge ». La cible est une couche N2 d’orchestration et de distribution qui agrège des rails existants et devient l’interface B2C, reseller et plus tard API/white-label.

N0 : MTN / Orange / CAMTEL / ENEO / autres producteurs ↓ N1 : agrégateurs / APIs / PSP sous contrat ↓ N2 : Qwifon Core catalogue · quote · routing · ledger · réconciliation · fraude · CRM · support · pricing ↓ B2C WhatsApp/Web | Revendeurs | API/White-label ↓ Clients finaux
Data/AirtimeAcquisition + fréquence. Potentiel élevé, marge à démontrer.
ENEO prépayéUrgence + ancrage + rétention. Très bon candidat produit héros.
Mobile MoneyRail de paiement. Ce n’est pas le produit final mais la colonne vertébrale.
Gaming/eSIM/SaaSCouche de marge future. Pas nécessaire à la V0.

Choix produit : les rapports divergent entre Data et ENEO. On ne tranche pas par opinion : la V0 doit supporter les deux et les faire combattre sur CAC, contribution nette, fiabilité, support et second achat J+7/J+30.

2. Architecture non négociable

  • Charlotte = interface conversationnelle : intention, qualification, aide, statut, relance consentie.
  • Core déterministe = argent et exécution : paiement, idempotence, API, ledger, remboursements, logs.
  • Pas de wallet client réglementé en V1. Le reseller peut avoir un compte préfinancé/stock numérique contractuel, sous réserve de validation juridique.
  • Pas de commission de recrutement. Le revenu du réseau vient de transactions finales payées, livrées et non remboursées.
  • Multi-fournisseurs à terme. Le moat est l’orchestration, la donnée transactionnelle et la qualité de reprise, pas le secret du fournisseur.

3. Build/Test — structure que l’agent doit approfondir

Mandat : construire d’abord un Transaction Lab capable de traiter ENEO prépayé + un rail Data/Airtime via WhatsApp/web et Mobile Money, avec preuve de paiement, livraison contrôlée, reçu, réconciliation et support d’incident.

3.3 State machine minimale

INITIATED → QUOTED → PAYMENT_PENDING → PAID → FULFILLMENT_PENDING → DELIVERED

Exceptions : PAYMENT_FAILED, FULFILLMENT_FAILED, RECONCILIATION_REQUIRED, REFUND_PENDING, REFUNDED.

Règle absolue : aucun timeout, retry ou message IA ne peut provoquer deux livraisons.

3.5 Gates Go / No-Go

  • Gate 1 : droit commercial écrit pour l’usage prévu.
  • Gate 2 : contribution nette positive sur transactions réelles.
  • Gate 3 : zéro double fulfillment sur le pilote.
  • Gate 4 : réconciliation quotidienne propre.
  • Gate 5 : incident et remboursement résolvables.
  • Gate 6 : support humain pour les exceptions.
  • Gate 7 : consentement WhatsApp + règles data validés.

3.6 Livrables obligatoires avant production

Architecture finale, ADRs, schéma DB, contrats API internes, state machine, threat model, gestion des secrets, matrice providers, calculateur d’économie unitaire, test plan, fixtures sandbox, runbook incident, dashboard, checklist conformité, plan de déploiement/rollback et critères Go/No-Go.

3.7 Interdictions V0/V1

Pas de wallet client réglementé, pas de microcrédit, pas de multi-pays, pas d’app native obligatoire, pas de commission de recrutement, pas d’ads massives avant instrumentation, pas de promesse « moins cher » sans preuve, pas de dépendance aveugle à un seul N1.

4. Ce que l’agent doit encore rechercher avant de coder en production

Les rapports donnent une direction, pas les valeurs finales. L’agent doit remplacer les inconnues par des preuves : prix N1, minimum deposit, SLA, settlement, refund policy, disponibilité catalogue, droit de sous-distribution, frais MTN/Orange, contraintes ENEO, fiscalité applicable, KYC et responsabilité en cas d’échec.

La bonne méthode n’est pas « approfondir puis tout construire ». C’est : question → preuve → décision → spec → test → métrique → gate.
